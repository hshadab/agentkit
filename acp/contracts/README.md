## Groth16Verifier

Verifies Groth16 zero-knowledge proofs generated by JOLT-Atlas for authorization decisions.

### Interface

```solidity
function verifyProof(
    uint[2] memory a,
    uint[2][2] memory b,
    uint[2] memory c,
    uint[1] memory input
) public view returns (bool)
```

### Parameters

**Proof Components**:
- `a`: Proof point A (2 field elements)
- `b`: Proof point B (2x2 field elements)
- `c`: Proof point C (2 field elements)

**Public Inputs** (1 element):
- `input[0]`: Encoded decision and confidence
  - Format: `decision * 10000 + confidence * 100`
  - Example: `18500` = authorized (1) with 85% confidence

### Returns

- `true`: Proof is valid (cryptographically verified)
- `false`: Proof is invalid

### Gas Cost

~300,000 gas per verification (includes pairing operations)

### Usage Example

```javascript
const proof = {
  a: ["0x123...", "0x456..."],
  b: [["0x789...", "0xabc..."], ["0xdef...", "0x012..."]],
  c: ["0x345...", "0x678..."]
};

const publicSignals = [
  "18500"  // Authorized with 85% confidence
];

const isValid = await verifierContract.verifyProof(
  proof.a,
  proof.b,
  proof.c,
  publicSignals
);

console.log("Proof valid:", isValid);
```

## Circuit Design

The Groth16 circuit verifies authorization decisions:

### Inputs

**Private Inputs** (not revealed):
- Authorization parameters (budget, trust, amount, etc.)
- Intermediate computation values

**Public Outputs**:
- Decision (0 = denied, 1 = authorized)
- Confidence (0-100, scaled by 100)

### Constraints

Circuit validates:
1. Budget check: `budget_remaining >= amount`
2. Trust check: `merchant_trust >= 0.5`
3. Amount check: `amount <= budget_remaining * 0.5`
4. Category check: `category_score > 0.5`
5. Velocity check: `velocity < 10`
6. Confidence calculation: `(passed_checks / total_checks) * 100`

**Total Constraints**: ~150 R1CS constraints (simplified demo circuit)

## Security Considerations

### Cryptographic Security

- **Proof System**: Groth16 (128-bit security level)
- **Curve**: BN254 (alt_bn128) for EVM compatibility
- **Trusted Setup**: Uses Powers of Tau ceremony from Hermez/Polygon

### Known Limitations

1. **Simplified Circuit**: Demo uses 2 public inputs instead of full 14-parameter model
2. **No Recursion**: Each proof verified independently (no aggregation)
3. **Gas Costs**: Verification is expensive (~300k gas per proof)

### Production Recommendations

1. Implement proof aggregation (batch verification)
2. Expand circuit to validate all 14 parameters
3. Add proof caching to avoid re-verification
4. Implement access controls (only authorized verifiers)
5. Add event logging for audit trail

## FAQ

### Why Base Sepolia?

- Low gas costs compared to Ethereum mainnet
- Active testnet with faucets
- Basescan explorer support
- Same EVM as mainnet (easy migration)

### Can I use this on mainnet?

Yes, but:
1. Audit the contract first
2. Test extensively on testnet
3. Consider gas optimization (aggregation)
4. Implement access controls

### How do I get testnet ETH?

- Coinbase Faucet: https://www.coinbase.com/faucets/base-ethereum-sepolia-faucet
- Alchemy Faucet: https://www.alchemy.com/faucets/base-sepolia
- Requires mainnet activity (~0.001 ETH on L1)

### What if verification fails?

Common causes:
- Proof generated with different circuit
- Public inputs don't match
- Proof corrupted in transmission
- Contract deployed with wrong verifying key

Check logs and regenerate proof with correct parameters.
